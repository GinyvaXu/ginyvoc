# GinyVoC 技术路线替代方案对比

> 当前路线：**原生 Web（HTML/JS）+ WebRTC mesh + Node.js(Socket.IO) 信令 + Electron 桌面壳**。
> 本文对比 5 条替代路线，给出特点、优缺点与适用场景，供版本规划决策。

## 〇、当前路线回顾

- 信令：Node.js + Express + Socket.IO（自研协议，房间/频道/成员状态机）
- 媒体：浏览器 WebRTC（Opus 语音 + VP8/VP9 屏幕），P2P mesh，每对端一条 RTCPeerConnection
- 桌面：Electron 壳内嵌信令服务器，NSIS/portable 打包
- 更新：自研 update.json 清单 + 静默安装（参考诺丁汉 updater.py）

**优点**：零媒体服务器成本；部署极简（单 Node 进程）；客户端免构建（原生 ES Modules）；自托管友好。
**代价**：mesh 上行带宽随人数增长（约 8 人上限）；Electron 包体较大；Web 客户端受浏览器安全策略约束（需 HTTPS 才能用麦克风）。

---

## 一、替代路线 A：保留 Web 客户端 + mediasoup SFU（自建转发服务器）

把“每对端一条 P2P”改为“每人一条到 SFU 的上行 + 订阅下行”。

| 维度 | 对比 |
|------|------|
| 架构改动 | 仅替换 webrtc.js 媒体层与 server 增加 media worker；房间/频道/信令协议不变 |
| 人数上限 | 几十人/频道（受服务器带宽/CPU 限制） |
| 部署复杂度 | 中：需 Node media worker、端口规划（RTC 端口段）、TURN 仍可能需要 |
| 服务器成本 | 每个活跃用户约 1 路上行 + N 路下行转发，带宽成本随规模上升 |
| 隐私 | 媒体过服务器（DTLS-SRTP 加密，服务器可解密转发） |
| 维护 | mediasoup 活跃维护，API 稳定，社区大 |

**优点**：保留现有前端与信令，升级路径最短；可平滑扩容。
**缺点**：需要一台带宽充足的服务器；复杂度明显上升。
**适合**：频道人数经常大于 8 的正式运营阶段。

## 二、替代路线 B：整体迁移 LiveKit（Go 全栈开源 SFU）

用 LiveKit 替换自研信令 + 媒体：客户端接 livekit-client SDK，服务器跑 livekit-server 单二进制。

| 维度 | 对比 |
|------|------|
| 架构改动 | 大：信令协议、房间模型、前端全部换成 LiveKit 生态 |
| 人数上限 | 高（官方支持数百人会议） |
| 部署复杂度 | 低：单个 Go 二进制 + Redis 可选；自带 TURN（coturn 集成） |
| 服务器成本 | SFU 模式，按带宽计费 |
| 隐私 | 媒体过服务器（默认） |
| 生态 | WebRTC 标准 + 官方 JS SDK；自托管许可证（免费版有并发限制） |

**优点**：功能完整（录制、转码、数据通道、webhooks），省掉大量自研信令工作。
**缺点**：丧失自研协议的灵活性与极简性；房间/频道模型要向 LiveKit 房间/参与者对齐；自托管免费版有并发限制。
**适合**：想快速获得企业级语音会议能力、不愿维护自研信令的项目。

## 三、替代路线 C：Go + Pion 全自研（harmony-server 式）

用 Go 写信令 + Pion WebRTC 媒体网关，单二进制部署。

| 维度 | 对比 |
|------|------|
| 架构改动 | 全部重写（换语言） |
| 人数上限 | 取决于自研质量，Pion 支持 SFU 也可 mesh |
| 部署复杂度 | 低：单二进制，跨平台 |
| 维护 | 需自己维护 WebRTC 细节（ICE/DTLS/SRTP），工作量大 |

**优点**：部署体验最好（单 exe）；性能好；可作为“一体化自托管”卖点。
**缺点**：从零重写成本最高；前端仍需浏览器 WebRTC。
**适合**：想彻底摆脱 Node 运行时、追求单文件分发的长期路线。

## 四、替代路线 D：原生桌面客户端（C++/Rust + Qt，Mumble 式）

放弃 Web 客户端，改原生桌面（如 Mumble/Murmur 客户端架构）。

| 维度 | 对比 |
|------|------|
| 架构改动 | 完全重写客户端 + 服务器 |
| 延迟 | 最优（原生音频栈，可做到局域网 <10ms） |
| 部署 | 需要每平台编译发布（Win/macOS/Linux） |
| 维护 | C++/Rust 开发成本高，UI 迭代慢 |

**优点**：性能与延迟天花板最高；不依赖浏览器安全策略。
**缺点**：开发/维护成本高；屏幕共享需自研采集与编码链路；不适合当前小团队快速迭代。
**适合**：追求极致低延迟的硬核开黑场景，或作为远期目标。

## 五、替代路线 E：Fork 现成开源项目（Galène / Mumble / harmony-server）

直接基于 Galène（Go, 轻量 WebRTC 会议）或 Mumble 改造。

| 维度 | 对比 |
|------|------|
| 架构改动 | 学习并改造他人代码，定制受限于上游设计 |
| 速度 | 最快起步 |
| 风险 | 上游协议/许可约束；深度定制困难 |

**优点**：立即可用，功能成熟。
**缺点**：品牌、UI、频道模型难以完全按自己想法定制；长期维护依赖上游。
**适合**：验证需求、不想维护核心媒体代码的阶段。

## 六、结论与建议

| 路线 | 改动量 | 上限 | 部署 | 成本 | 建议 |
|------|--------|------|------|------|------|
| 当前 mesh | 0 | 约 8 人/频道 | 极简 | 最低 | **现在**（已验证可用） |
| A. mediasoup SFU | 小 | 几十人 | 中 | 中 | 频道 >8 人时的首选升级 |
| B. LiveKit | 大 | 数百人 | 低 | 中 | 追求完整功能矩阵时整体迁移 |
| C. Go+Pion | 全部 | 中 | 最低 | 高 | 远期单文件分发目标 |
| D. 原生客户端 | 全部 | 高 | 高 | 最高 | 不做首期 |
| E. Fork 开源 | 中 | 视上游 | 中 | 低 | 备选，不推荐主路线 |

**建议路径**：v0.x 继续打磨当前 mesh + Electron 路线（权限、持久化、重连、自动更新）；当单频道人数超过 8 时，优先按路线 A 增加 mediasoup SFU（改动可控、信令协议不变）；若未来转向完整会议产品，评估路线 B 的整体迁移成本。

## 七、配套选型对比（非媒体部分）

| 项 | 当前 | 替代 | 说明 |
|----|------|------|------|
| 自动更新 | 自研 update.json + NSIS /S（诺丁汉式） | electron-updater | electron-updater 成熟省事，但依赖 GitHub 或自有发布源；自研方案国内代理可控性更好 |
| 打包 | electron-builder (portable/nsis) | electron-forge / tauri | Tauri 包体约 5MB、内存低，但需 Rust 工具链，且内嵌 Node 信令服务器需重写 |
| 日志 | 自研 logger 双写文件 | electron-log / winston | 自研已满足 Debug 要求，可后续换 electron-log 补 UI 面板 |
| 状态持久化 | 内存态 | SQLite(better-sqlite3) / 低版本 JSON 文件 | 先落 JSON/SQLite，账号体系再上 Redis |
